# EnvDock 平台版本与发布策略

## 功能基线

macOS 和 Windows 使用同一套 React、TypeScript、Rust、SQLite schema、IPC 契约和请求引擎。功能变更先落在共享源码，再由 [macOS / Windows 功能对照](macOS-feature-matrix.md) 核对两端行为。

平台差异只允许出现在构建配置、应用包、数据目录、系统窗口、文件选择器、密钥保护和系统 API 适配层。禁止为了平台差异复制业务功能、维护两套请求编辑器或让某个平台悄悄缺少业务入口。

## 版本号

同一功能基线使用同一组主次版本，平台发布序号使用奇偶区分：

- macOS 使用偶数发布号，例如 `2.0.0-macos`。
- Windows 使用奇数发布号，例如 `2.0.1-windows`。
- 版本号的差异只标记交付平台，不代表功能分叉；功能是否一致以共享提交和功能矩阵为准。
- 当前已完成的是 macOS `2.0.0`。Windows 对应包需在 Windows 构建机完成后，以奇数发布号生成并验证。

每个平台的标签采用 `v<version>-macos` 或 `v<version>-windows`，发布说明必须写明共享源码提交、平台构建环境、验证范围和未完成的架构启动验证。

## GitHub 保留规则

GitHub 的 Releases 和平台交付目录只保留每个平台当前最终版本：

- macOS：保留最新 `v2.0.0-macos`。
- Windows：待对应奇数版本完成构建后，只保留该 Windows 最终版本。

旧版本不作为当前下载入口；清理旧 Releases 和旧平台标签前，先确认对应 DMG/EXE、校验文件和迁移说明已经由当前版本接替。Git 历史仍可通过提交对象恢复，工作区交付目录不纳入源码仓库。

## 发布检查

发布前必须完成：

1. 共享功能矩阵逐项核对，确认两个平台没有业务入口差异。
2. 平台专属测试、构建、签名和安装启动验证。
3. `npm run check:version`、依赖审计、前端测试和 Rust 测试。
4. 只上传当前平台最终包、校验文件、许可证和安装说明。
5. 在 GitHub Release 中注明另一平台的对应版本是否已经完成；未构建的平台不能标记为已发布。
